  三、关键并发点详解

  3.1 爬虫层并发（parallel_fetch, scanner.py:445）

  Playwright 动态爬虫 (browser_crawler.py:225-242)：
  - 单个 BrowserContext 实例，所有并发页面共享
  - asyncio.Semaphore(thread_num) 限制并发页面数
  - asyncio.gather() 发起全部任务
  - 失败 URL 用 httpx 补救（fetch_urls_async 再请求一轮）

  httpx 静态爬虫 (httpx_crawler.py:113-177)：
  - 单个 httpx.AsyncClient，带连接池限制 Limits(max_connections=thread_num)
  - 同样 Semaphore + gather 模式
  - 智能请求模式（fetch_urls_smart）：两轮（POST → 405 回退 GET），串行两阶段

  并发控制参数：
  - parallel_fetch 内两个分支相互独立，各自的 Semaphore 互不影响
  - get_source_async 接收 args.thread_num
  - fetch_urls_async 限制 min(args.thread_num, 50)

  3.2 递归扫描并发（_scan_recursive, scanner.py:558）

  深度 0: process_single_batch → gather(dynamic, static) → 处理结果 → AI分析 →
  去重
  深度 1: process_single_batch → ...
  深度 N: ...

  - 深度遍历是递归串行的（DFS），每层内批次串行，批次内并发
  - 批次间 asyncio.sleep(BATCH_SLEEP=0.2s) 限速
  - 内存熔断 _check_memory_and_handle() 每批次后检查

  3.3 AI 分析层并发（params_scan.py）

  Level 2（Judge） 和 Level 3（Advisor） 存在严重并发瓶颈：

  # Level 2: 串行逐个调用 LLM（params_scan.py:287-328）
  for candidate in candidates:                  # ← for 循环，一次一个
      result = client.chat(...)                 # ← 同步阻塞调用

  # Level 3: 同样串行（params_scan.py:458-485）
  for candidate in level_2_candidates:          # ← for 循环，一次一个
      analysis_result = self.analyze(...)       # ← 同步阻塞调用

  client.chat() 是同步阻塞的 — 使用的是 OpenAI()（同步客户端）而非
  AsyncOpenAI()。每次调用会阻塞整个事件循环，导致所有并发任务在 LLM
  调用期间停滞。

  3.4 敏感信息扫描并发（secret_scanner.py）

● 说实话，算不上"混乱"——整体架构是清晰的，但并发纪律上确实比较混乱，是那种"看起
  来有条理、用起来到处卡"的状态。

  好的方面（不混乱）

  1. Scanner 主流程的 pipeline 结构清晰：_scan_recursive → 分批 → parallel_fetch
  → 处理 → AI → 下一层，层次分明
  2. Semaphore 控制并发上限：爬虫层都有 Semaphore 保护，不会无限制地发请求
  3. 信号量、Lock、容量限制都有：title_map 有 MAX_TITLE_PER_DOMAIN、Bloom filter
  无锁但位操作原子安全
  4. 资源清理有保障：finally、@asynccontextmanager、atexit 都在

  混乱的地方（核心问题）

  1. 同步 SDK 塞进异步事件循环（最致命）

  # ai_client.py:278
  self._client = OpenAI(...)  # ← 同步客户端
  # 但被大量地放在 asyncio 流程里调用:
  asyncio.run(scanner.run())
    → _scan_recursive()
      → _process_ai_batch()
        → _run_ai_and_validate()
          → ai_auditor.scan_multiple_apis()
            → _analyze_multiple_api_values()
              → client.chat()  # ← 同步阻塞 10-30秒！

  后果：asyncio.gather 本意是并行，结果一个 LLM
  调用阻塞事件循环，所有协程排队等。名义上是异步并发，实际上是排队串行。

  2. AI 分析内部 for 循环串行调用 LLM

  # params_scan.py:287
  for candidate in candidates:              # 一个一个来
      result = client.chat(...)             # 同步阻塞 × N

  Level 2 和 Level 3 都是这种模式。20 个 API → 20 次 LLM 调用 →
  全部串行。如果改成 asyncio.gather + AsyncOpenAI，20 个可以同时跑。

  3. run_in_executor 用得很"别扭"

  # request_executor.py:234
  result = await loop.run_in_executor(None, execute_api_request, ...)

  execute_api_request 是同步 httpx 函数，包一层 run_in_executor
  扔到线程池——能用但很奇怪。既然 httpx 支持异步，直接 await client.get()
  就行，何必绕线程池？说明设计时没想清楚。

  4. 配置热更新用 Thread，模型调用却是 Sync

  ConfigWatcher
  是后台线程挺合理的，但它的存在意义是"热更新模型列表"——结果模型调用的 chat()
  本身却是同步阻塞的，这和"热更新"的初衷有点矛盾。

  ---
  一句话总结

  ▎ 架构不乱，但异步纪律乱。

  pipeline 设计是好的，爬虫层的并发也是好的——问题出在"写了异步框架，但核心
  IO（LLM 调用）用的是同步
  SDK"，导致整个并发设计在关键的瓶颈环节完全失效。修复一个点就够了：OpenAI() →
  AsyncOpenAI()，然后 LLM 调用处用 asyncio.gather 并行化。
